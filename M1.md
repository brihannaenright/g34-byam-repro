# G34 Student Workbook M1 Plan

## 1. Research Questions and Target Result

### RQ1
**Question:** On a fixed sample of BUMP breaking updates, does Byam with DeepSeek V3 reproduce the paper's reported build success rate (BSR) and error fix rate (CEFR) for the baseline prompt (P1) and the full-context prompt (P8)?

- **Source Anchor:** Reyes et al.., 4.3.1 Protocol for RQ1; Section 5.1 RQ1 Repair Success, Table 4
- **Target Result:** Reproduces the finding that DeepSeek V3 can successfully repair a proportion of real-world breaking dependency updates, where a successful repair means that the updated project builds successfully after applying the LLM-generated fix
- **Out of Scope:** Reproducing the complete 103-case experiment, all five LLMs, all eight prompt configurations, and the entire Byam evaluation is outside the scope of M1. The reproduction will use only the pre-declared bounded sample
### RQ2
**Question:** Can Byam be refactored to work with a newer model, such as Claude Opus, to improve its error fix rate for baseline prompt (P1) and the full-context prompt (P8)?

- **Source Anchor:** Reyes et al.., 4.3.2 Protocol for RQ2
- **Target Result:** Determine the error fix rate achieved by the refactored version of Byam using Claude Opus with prompts P1 and P8, and compare these results with the corresponding results reported for Byam in the original study.
- **Out of Scope:** Evaluation of models other than Claude Opus, prompts other than P1 and P8, and experiments or results outside the bounded sample defined for this reproduction. We will also not investigate changes to Byam's underlying repair approach beyond the modifications required to support Claude Opus.
### RQ3
**Question:** With current-generation models, such as Claude Opus, does P8 still beat P1, or does the benefit of added context shrink as models get stronger?

- **Source Anchor:** Reyes et al., 3.3 Step 2: Use LLM to Generate Repairs, Table 2; Section 5.1 RQ1 Repair Success, Table 4; Section 5.2 RQ2 Partial Repair, Table 6
- **Target Result:** Check whether Claude Opus fixes more builds and compilation errors with P8 than P1. Compare that gap with DeepSeek V3 on the same sample to see whether Claude Opus benefits less from P8's extra information.
- **Out of Scope:** We will only test Claude Opus and DeepSeek V3 using P1 and P8 on the selected sample. We will not test other prompts, check each part of P8 separately, or claim that the results apply to all newer models.
## 2. The Bounded Sample

- **Unit of analysis:** One eligible Java breaking-dependency update case
- **Source/version:** The BUMP breaking dependency update cases provided through the artists replication artefact. The exact repository version/commit used will be recorded before execution
- **Size/range:** 12 eligible breaking dependency update cases
- **Selection rule:** Select the first 12 cases in stable order by case ID, then file path, then chronological ID. If fewer than 12 cases are available, use all available cases and record this.
  **Recorded before execution:** BACARDI `4bc6b254dea54a70ed9cbac32836cddc38ee6e4a`, BUMP `324d5513aa5ca40b5cb32de5b816a58fa60bd7bb` (`env/commits.txt`). Selected cases: `sample/g34-sample.txt`.

## 3. Method

- **Inputs:** Pre-declared Java breaking dependency update cases, including the affected client code, dependency update, compilation/build failure information, error message and the contextual information required by the selected prompt configuration
- **Procedure:** For each selected case, reproduce the breaking dependency update and capture the resulting compilation failure. Construct a fixed LLM prompt using the pre-declared prompt configuration and provide the relevant client code and failure/context information. Apply the LLM-generated repair to the client-code, rebuild the project and run its existing tests. Record whether compilation succeeds, whether tests succeed, and whether new failures/errors are introduced.
- **Output/Decision:** BSR = number of successfully fixed builds / number of initially failing builds
## 4. Expected Result

We expect the LLM to successfully repair some, but not all, breaking dependency updates. Based on the original study, richer contextual information such as the erroneous line and API differences is expected to improve repair performance in at least some configurations compared with the baseline prompt.

| Outcome | Meaning |
|---|---|
| **REPRODUCED** | The bounded run provides valid evidence that the LLM can successfully repair breaking dependency updates, with at least one case achieving a complete repair (successful compilation and tests), and the observed effect of additional contextual information is directionally consistent with the corresponding original result. |
| **NOT REPRODUCED** | The bounded experiment executes successfully on all eligible selected cases but produces no successful complete repairs, or the tested contextual-information relationship clearly contradicts the corresponding original finding. |
| **INCONCLUSIVE/BLOCKED** | The experiment cannot be validly evaluated because required dependencies, builds, LLM access, API-difference information or other required artefacts cannot be obtained or executed reliably. |
